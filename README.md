# SQL-исследование e-commerce витрины

Восемь бизнес-вопросов к базе интернет-магазина из 11 связанных таблиц.
Вся аналитика — на чистом SQL: CTE, оконные функции, рекурсивный обход
иерархии. Ни строчки Python в самих расчётах.

**Итоговый отчёт с находками → [REPORT.md](REPORT.md)**

---

## Быстрый старт

```bash
./run_all.sh
```

Генерирует базу (~15 сек), создаёт представления, прогоняет все восемь
запросов и проверки качества данных. Результаты — в `results/`.

Требуется: `sqlite3` 3.28+ и `python3` (только стандартная библиотека,
никаких зависимостей).

## Проверка, которая никогда не падала, не проверена

В `99_data_quality_checks.sql` двадцать проверок, и на приложенной базе все
двадцать дают `OK`. Само по себе это не значит ничего: отчёт из зелёных строк
одинаково выглядит и когда данные в порядке, и когда проверка написана так, что
не сработает никогда.

`tests/` вносит в копию базы ровно один дефект и требует, чтобы покраснела
именно та проверка, которая его ищет:

```bash
pip install pytest && python -m pytest tests -q   # 24 теста, ~6 секунд
```

Пятнадцать дефектов - сирота в `order_items`, платёж по несуществующему заказу,
возврат раньше заказа, скидка 150%, возврат по отменённому заказу, пропавший
месяц в календаре, изменённая сумма платежа. Плюс три наблюдения, которые
вылезли при написании этих тестов:

- **Часть проверок раздела B недостижима на этой базе**: `quantity <= 0`,
  нулевой возврат и неизвестный статус заказа запрещены `CHECK`-ограничениями
  схемы, то есть такую строку сюда просто не записать. Проверки не лишние -
  витрину можно залить и мимо ограничений, - но в тестах они проверяют схему,
  а не SQL-запрос, и помечены отдельно.
- **Дефекты бывают связанными.** Скидка 150% красит две проверки: свою и
  сходимость денег, потому что меняет сумму позиции. Это правильно, и тест это
  фиксирует, чтобы отчёт с двумя красными строками не выглядел как две
  независимые поломки.
- **Ровно один дефект должен красить ровно одну проверку**, когда он
  изолированный: отдельный тест на это есть.

CI прогоняет эти тесты и, кроме того, пересобирает витрину генератором с нуля и
сверяет `results/` до байта - генератор детерминирован, поэтому цифры в отчётах
можно проверить, а не принять на веру.

## Что здесь можно посмотреть по технике SQL

**Оконные функции** — используются по делу, а не для галочки:

| Функция | Где и зачем |
|---|---|
| `SUM() OVER (ORDER BY ... ROWS UNBOUNDED PRECEDING)` | накопленная доля выручки для ABC-анализа (07) |
| `AVG() OVER (ROWS BETWEEN 6 PRECEDING AND 5 FOLLOWING)` | центрированное скользящее среднее для декомпозиции сезонности (04) |
| `LAG(..., 12)` | сравнение год к году по непрерывному помесячному ряду (04) |
| `LAG()` + `FIRST_VALUE()` | конверсия шага воронки и сквозная конверсия (03) |
| `ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_ts)` | порядковый номер заказа в жизни клиента (08) |
| `CUME_DIST()` | медиана и p90 интервала между покупками — в SQLite нет `PERCENTILE_CONT` (08) |
| `NTILE(5)` / `NTILE(10)` | квинтили RFM (05) и децили каталога (07) |
| `RANK()` / `DENSE_RANK()` | расхождение рейтингов по выручке и по прибыли (02) |
| `PERCENT_RANK()` | положение клиента в базе по деньгам (05) |
| накопительный `SUM() OVER (PARTITION BY ... ORDER BY ...)` | кривая LTV по месяцам жизни когорты (06) |
| `WINDOW w AS (...)` | именованное окно, чтобы не дублировать кадр (04, 08) |

**Рекурсивный CTE** — подъём от листовой категории к корню дерева
(`v_category_tree` в 00). Дерево сейчас двухуровневое, и хватило бы
self-join, но рекурсия не потребует переписывания при добавлении третьего
уровня.

**Ловушки, которые разобраны прямо в комментариях к запросам:**

- **Правая цензура в когортах** (01) — у свежей когорты нет данных за M+3;
  ноль вместо `NULL` завалит средние по столбцу.
- **`NTILE` рвёт группы равных значений** (05) — 58% клиентов имеют ровно
  один заказ, и `NTILE(5)` растаскивает их по трём квинтилям. Показано на
  данных, поэтому F размечается порогами, а не квинтилями.
- **`WHERE` отрабатывает раньше оконных функций** (04, 06) — если прореживать
  ряд до окна, индексы и накопленные доли посчитаются по выборке вместо
  полного ряда.
- **Неравное число наблюдений по месяцам** (04) — данные обрываются на
  августе, поэтому группировка по номеру месяца по всем годам завышает
  первую половину года. Считается по полным годам.
- **Дубли при join'е возвратов** (00) — на одну позицию может быть несколько
  возвратов; без предварительной свёртки выручка задваивается.
- **Незрелые когорты в LTV** (06) — деление накопленной выручки на всю базу
  занижает LTV, потому что свежие когорты размывают знаменатель.

## О данных

Данные **синтетические**, сгенерированы
[`data/generate_ecommerce_db.py`](data/generate_ecommerce_db.py) с
зафиксированным seed — база воспроизводится до строки.

Причина в том, что задача требует посчитать маржу по категориям и воронку,
а ни Chinook (59 клиентов, нет себестоимости), ни UCI Online Retail (одна
плоская таблица), ни Olist (нет себестоимости) не содержат одновременно
себестоимости и лога событий. Подробное обоснование, список заложенных в
генератор закономерностей и честный перечень ограничений — в разделах 1 и 4
[отчёта](REPORT.md).

Корректность методики проверяется независимо: декомпозиция сезонности в
запросе 04 восстановила заложенные генератором коэффициенты (ноябрь — 1,66
против заложенных 1,70, февраль — 0,756 против 0,75), ничего не зная о
генераторе.
